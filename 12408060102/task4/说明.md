# task4 Redis Pipeline 与性能比较（选做）

个人参数：S=2，C=2 → **N = 1000 + 100*C + S = 1202**，每批最多 **Q = 100**。

## 文件
| 文件 | 作用 |
| --- | --- |
| `task4.py` | 方案甲（逐条写入）+ 方案乙（普通 Pipeline，每批 ≤100）+ 完整性核验 + 计时 |
| `result.txt` | 运行输出 |

## 运行
```bash
python task4.py
```

## 要点
- 方案甲：`for i in 1..N: rc.set(key, value)`，每条收到返回后再发下一条，不使用 Pipeline / 多线程 / 异步。
- 方案乙：`rc.pipeline(transaction=False)`，每批最多 100 条，`execute()` 取回整批结果后再进入下一批；尾批用 `min((b+1)*Q, N)` 处理。
- 计时：`time.perf_counter()` 覆盖命令构造、发送与回复接收，最后一批回复收齐才停表。
- 完整性核验：两种方案都分批 GET 全部 1202 个键并比对值，均为 **1202/1202** 正确。

## 结果
| 指标 | 值 |
| --- | --- |
| 命令总数 | 1202 |
| Pipeline 批次数 | 13 |
| 最后一批数量 | 2 |
| 方案甲耗时 | 196.30 ms |
| 方案乙耗时 | 43.34 ms |

结论：Pipeline 明显更快（约 4.5 倍）。本机回环 RTT 极低、且 redis-py 集群 Pipeline 每条命令要先算槽并按节点分组，因此收益没有达到数量级；若差异不明显，常见原因是数据量太小、RTT 本来就低、批大小过小、客户端每批后额外同步，或服务端单线程已成瓶颈。
