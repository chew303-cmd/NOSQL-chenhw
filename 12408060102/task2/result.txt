第二题 MongoDB 原子扣减与事务验证
参数：S=2 A=2 C=2  Stock=5+C=7  Buy=1+A=3  bookId=BOOK-12408060102

== 1. 原子扣减：find_one_and_update 一次完成“条件检查 + 扣减” ==================
filter = {"_id": "BOOK-12408060102", "stock": {"$gte": 3}}   update = {"$inc": {"stock": -3}}
数据库返回：扣减成功，扣减后库存 = 4（OK）
当前库存：4，订单数：0

== 2. 判断操作结果（三种分支都由数据库返回值决定） =============================
场景        状态码     说明
---------------------------
库存充足     OK         扣减成功，扣减后库存 = 0
库存不足     NO_STOCK   库存不足或教材不存在，未执行扣减
执行异常     DB_ERROR   OperationFailure: Cannot increment with non-numeric argument: {stock: "NaN"}
判定依据：返回文档=成功；返回 None=库存不足/教材不存在；抛 PyMongoError=执行异常。
（不看程序执行到哪一行，只看数据库这一次操作的返回结果。）

== 3. 事务：库存扣减 + 订单插入，同一 session、同一事务 ========================
正常订购 order(forceError=False) -> True（事务提交成功），库存=4，订单=1
故障订购 order(forceError=True)  -> False（RuntimeError: 模拟故障：库存已扣减、订单插入前主动抛出异常）
回滚后库存=7（应仍为 7），订单=0（应为 0）

== 4. 系统测试：每场景独立重置，实际结果与程序计算的预期值比较 =================
场景             初始库存      购买量     成功    失败    最终库存      订单数     核验
---------------------------------------------------------------------------------------
T1 正常订购    7         3       1     0     4         1       PASS
T2 库存不足    2         3       0     1     2         0       PASS
T3 中途异常    7         3       0     1     7         0       PASS
T4 连续购买    7         3       2     1     1         2       PASS
说明：T4 共发起 ⌊7/3⌋+1 = 3 次订购，预期成功 2 次、剩余 1 本。

== 5. 结果解释 =================================================================
(1) 为什么单次扣减具有原子性，仍然需要事务？
    单文档扣减只能保证“库存”这一个文档不被并发改坏；而订购业务要同时改两个文档
    （inventory 与 orders）。如果扣减成功、插入订单时进程崩溃或抛异常，库存少了却
    没有订单，账就对不上。事务把两次写入绑成一个整体：要么都提交，要么都回滚。
(2) forceError 测试验证了什么？
    T3 在库存扣减之后、订单插入之前主动抛异常。回滚后库存仍是 7、订单数为 0，
    证明事务确实撤销了已经执行的扣减，说明“扣减成功但订单没落库”这种半成品状态
    不会留在数据库里；同时也说明结论必须以“提交成功”为准，而不是以扣减返回成功为准。
